Unikraft (app-elfloader/nginx) におけるシステムコール変換とVMI観測可能性の検討
（2026-07-06 まとめ）

============================================================
0. そもそもシステムコール監視は必要か
============================================================
- Unikraftには CONFIG_LIBSYSCALL_SHIM_STRACE というゲスト内straceが既に
  存在する（Phase 4 で ground truth として使用済み）。「システムコールを
  見る」だけならこれで足りる。
- しかしこれは「ゲスト自身が自分の挙動を報告する」方式であり、ゲストが
  侵害・改造された場合は信頼できない（agentベース観測の限界）。
- VMIはゲストの自己申告に依存せず、ハードウェア境界の外（ホスト側）から
  事実を観測する。
- 3章で示す通り、Unikraftのバイナリ互換syscallはデフォルトでホストに
  一切見えない（VM Exitを起こさない）。つまり「ホストから見てゲストが
  何のシステムコールを呼んだか」は自明ではなく、これを可視化する行為
  自体に価値がある。
→ 結論: ゲスト内観測は信頼境界の外に置けない。ホスト外部からの観測
  （VMI）が必要な理由は、Unikraftのsyscallがホストに素通しで見える
  わけではないから。

============================================================
1. Unikraftでのsyscall変換メカニズム
============================================================
根拠ファイル: plat/common/include/x86/cpu.h:269-279

    wrmsrl(X86_MSR_STAR, (0x08ULL << 48) | (0x08ULL << 32));
    wrmsrl(X86_MSR_LSTAR, (__uptr) _ukplat_syscall);

- STARのCS/SSセレクタが両方 0x08（同一リング = リング0固定）。
  Linuxのような ring3 -> ring0 の特権遷移は存在しない。
- x86の syscall 命令自体は、CPUマイクロアーキ的にRIPをLSTAR
  (= _ukplat_syscall) へ差し替えるだけの命令レベルジャンプ。
  Unikraftはこれを「トラップ」ではなく「関数呼び出しの皮を被った命令」
  として使っている。
- 実行順序:
  nginx (unmodified ELF) が syscall 命令発行
    -> CPUがLSTARへジャンプ (_ukplat_syscall, plat/common/x86/syscall.S)
    -> syscall.S がトラップフレーム(struct uk_syscall_ctx)を構築
    -> ukplat_syscall_handler() (lib/syscall_shim/uk_syscall_binary.c:68)
    -> uk_syscall6_do_e() が rax(syscall番号) をディスパッチテーブルで
       引いて対応する uk_syscall_r_<name>() を呼ぶ
       (vfscore/lwip/uktime等の各ライブラリが提供する実装)
- ここまで全部、同一アドレス空間・同一リング内の関数呼び出し連鎖。

============================================================
2. 変換された関数のゲスト側実行
============================================================
- uk_syscall_r_* はUnikraft内の通常のCライブラリ関数で、ゲストVMの
  CPUコンテキスト内で最初から最後まで完結する。
- syscall.S内の cli/sti (IRQ無効化区間) はCPU特権命令であって
  VM Exitではない -- KVMが許可している限りゲスト内で処理される。
- 「ゲスト側実行」はLinuxのカーネル空間実行と見た目は同じ
  (syscall命令からリターンまで) だが、実体はUnikraftライブラリの
  通常の関数コールである。

============================================================
3. (2)がホスト側でどう実行されるか
============================================================
- 重要な発見: 大半のsyscallはホスト側で何も起きない。
- VM Exitが発生するのは、その uk_syscall_r_* 実装が実際にホストの
  介在を要する操作 (virtio-net宛のMMIO/PIOアクセス、割り込み、
  タイマ関連MSR等) を行った場合のみ。
  例: gettimeofday がTSCを直接読むだけならVM Exit不要。
      accept4/recvfrom は最終的にvirtio-netのMMIOに触れて初めて
      ホストに見える。
→ これが、既存ツールが _ukplat_syscall にソフトウェアブレークポイント
  (int3) を仕掛けている理由の技術的根拠になる。syscall発行という事象
  自体はホストに自然には見えないため、人工的にトラップを作らないと
  観測点が存在しない。
→ README Phase 3 の 95-99% オーバーヘッドは、「本来ホストに見えない
  はずの処理を無理やり見えるようにするコスト」として説明できる。

============================================================
4. 引き続きLibVMIで監視できるか
============================================================
- 既存メモリ(vmi_libvmi_infeasibility)の結論は変わらない:
  Xen backend / KVM modern(kvmi) backend / KVM legacy(pmemaccess)
  backend いずれも本ホストでは不可 (詳細は該当メモリ参照)。
- 今回の分析はこの結論に理論的な補強を加える: LibVMIが使えたとしても、
  3章の事実 (syscall自体はVM Exitを起こさない) から、LibVMIの
  breakpoint/EPT-violationイベントAPIも結局は現行のGDB int3と
  同じ原理 (人工的トラップの注入) に依存するしかない。
- つまりLibVMIに切り替えても「95-99%オーバーヘッド」という性質自体は
  変わらず、変わるのはトラップ後の通知経路
  (QEMU gdbstubのテキストプロトコル往復 vs kvmiのイベントAPI) だけ。
- TCG pluginアプローチが有望なのは、これが唯一「トラップではなく
  エミュレーション内フックとして無料で観測できる」経路だから。

============================================================
5. 通常システム（ring0/ring3分離のあるLinux）との比較
============================================================
[syscall変換メカニズム]
- 通常Linux: entry_SYSCALL_64もSTAR MSRを使うが、CS/SSはring0用/ring3用
  で別々。syscall命令実行時にCPLが3->0へ実際に変わる。カーネルページは
  U/Sビット・SMEP/SMAPでユーザから読めない(ハードウェア強制の壁)。
- Unikraft: 1章の通りCS/SSが両方0x08=ring0固定。特権遷移が存在しない。

[ゲスト側実行]
- 通常Linux: sys_read等はユーザとは別の信頼領域。copy_from_user/
  copy_to_userで検証してから使う。カーネルがバグってもユーザプロセスは
  直接カーネルメモリを書けない(脆弱性がない限り)。
- Unikraft: uk_syscall_r_*はnginxと同じアドレス空間・同じ特権レベルで
  動く通常の関数呼び出し。呼び出し元/先の間に検証境界がほぼない。

[ホスト側可視性 - 実は共通点が多い]
- 通常のゲストOS(KVM上のLinux)でもsyscall命令自体はVM Exitを起こさない
  (SYSCALL/SYSENTERはVM Exit契機の命令リストに入っていない)。これは
  Unikraft固有ではなく仮想化一般の性質。
- 差が出るのはその後: 通常ゲストは複数プロセス/CR3切り替え/ページ
  フォルト/スケジューラのタイマ割り込みなどで頻繁にVM Exitが自然発生し、
  これがVMIツール(DRAKVUF等)の「ついでの観測機会」になる。
  Unikraftは単一プロセス・静的マッピング・単一アドレス空間のため
  この副次的Exitがほぼ無く、観測点は_ukplat_syscallへの人工的
  ブレークポイントのみ、という選択肢の少なさが固有の弱点。

[オーバーヘッド]
- Phase 3の95-99%低下はUnikraft特有の現象ではない。通常ゲストに対して
  DRAKVUF等でsyscallを全件int3/EPTフックしても同種の重いオーバーヘッド
  が文献で報告されている(本番のEDRが「全syscallトラップ」を避け対象を
  絞る理由)。メカニズムは共通、違うのは緩和策の選択肢の多さ。

============================================================
6. Unikraftで「侵害された瞬間」の具体例
============================================================
[侵害の起点]
nginxはUnikraft向けに書き換えたコードではなく、app-elfloaderがバイナリ
互換モードでロードする無改造のLinux ELF。攻撃対象は通常のnginxと同じ:
- HTTPリクエスト/レスポンスパーサのバッファオーバーフロー
  (chunked encoding、range header等)
- リンク済みライブラリの脆弱性 (PCRE、zlib CVE-2018-25032系、
  OpenSSL heap over-read系、resolver overflow CVE-2021-23017系)
つまりUnikraft固有の新しい攻撃ではなく、既存nginx/CVE知識がそのまま
通用するという前提。

[ビルド設定から確認した侵害後の違い]
実際のビルドログ(.unikraft/build/*.cmd)で確認:
  -fno-stack-protector -fcf-protection=none -fno-PIC -no-pie
かつ .unikraft/build/config で `CONFIG_OPTIMIZE_PIE is not set`。
Kraftfileでは CONFIG_LIBPOSIX_USER_UID/GID: 0 (root固定)。
つまりUnikraftライブラリ側には:
  - スタックカナリアなし
  - CET/CFIなし
  - ASLR/PIEなし(固定アドレス)
が揃っている。これに1章のring0固定(特権境界なし)が重なる。

[起点=終点への崩壊]
- 通常Linux: nginxのオーバーフローを突いても得られるのはwww-data権限の
  プロセス。root/カーネル権限を得るには別のカーネル脆弱性による特権
  昇格が必要(ASLR/カナリア/SMEP/SMAPがこれをさらに困難にする)。
- Unikraft: 同じバグで得られるコード実行がそのままring0(特権境界が
  ない)。アドレス固定でROPガドレット探索も容易。カナリア/CFIもない。
  → 通常システムの「2段構えの攻撃チェーン(ユーザ空間RCE->カーネル
    権限昇格)」が、Unikraftでは1段目のRCEがそのまま最終ゴールになる。

[侵害後に可能になること]
ring0+固定アドレス空間を得た攻撃者は、ゲスト内で任意の物理メモリ/
ページテーブルの読み書き、MSR(X86_MSR_LSTAR自体を含む)の書き換え、
割り込み無効化、CONFIG_LIBSYSCALL_SHIM_STRACEのような自己申告的
観測機構の無効化・偽装が可能。
→ 侵害された瞬間、ゲスト内部の観測手段(strace、ログ)は攻撃者の制御下
  に入り信頼できなくなる。ハイパーバイザ側(ホスト)からの外部観測=VMI
  でしか、侵害後も信頼できる観測を継続できない。0章の主張の具体的な
  裏付け。

7. 訂正: 「特権昇格が存在しない」はUnikernelの弱点ではなく
   利点の裏返しである(6章の補足・重要な訂正)
============================================================
6章の書き方は誤解を招く。「特権昇格が存在しない」ことそのものは
Unikernelの本来の売り文句であり、矛盾しているわけではない。整理すると
別の2つの機能が同じハードウェア機構(ring分離)の上に乗っていた:

  (1) テナント間分離: 複数の相互不信なプロセス/ユーザを同居させるために
      必要な境界。Unikernelは「1つのアプリしか動かさない」設計なので、
      そもそも守るべき他テナントがいない -> この境界のコスト(汎用
      ドライバ、多重化されたFS、CVEの多いカーネルサブシステム群)を
      丸ごと削れる。これは本物の攻撃対象(TCB)削減であり、Unikernelの
      正当な強み。
  (2) 同一アプリへの多層防御: 外部攻撃者がnginxを一段乗っ取っても、
      その先にもう一段の壁がある、という「侵害確率とは別の、被害範囲を
      限定する」機能。これは「他テナントがいるから」ではなく「同じ
      アプリの被害範囲を限定するため」に存在する壁。

(1)を削ると副作用として(2)も一緒に消える(同じring分離を共用している
ため)。Unikernelの設計思想は侵害の"確率"を下げる(コード量削減=バグの
絶対数減少)ことに主眼があり、侵害"された場合の被害"を抑える多層防御の
役割までは代替していない。つまり6章の内容は:

  攻撃対象は減ったが、侵入された場合の被害は増えた(トレードオフ)

というのが正確な言い方であり、Unikernelの良さ(1)と矛盾しない。

さらに、この検証対象(app-elfloaderのバイナリ互換モードで動く無改造
nginx)は(1)の恩恵もフルに受けていない: 削減されているのは「カーネル
側」(Unikraftが実装するsyscall数、不要なドライバ、マルチユーザ機構)
だけで、「アプリ側」(nginx本体+libpcre/zlib/openssl)の攻撃対象は通常の
nginxと全く同じ、1個も削れていない。本来のUnikernel純正アプリ(Unikraft
API向けに書き直し、必要な機能だけリンク)であれば(1)の効果をアプリ側
にもフルに享受できるが、バイナリ互換モードは移植の楽さを優先してその
効果を放棄している。つまりこのビルドは、Unikernelの強み(攻撃対象削減)
をあまり享受できておらず、弱み(多層防御の欠如)だけを比較的強く受けて
いる、という検証対象固有の位置づけになる。

8. バグ・脆弱性・攻撃・エクスプロイトの区別
============================================================
- バグ: 実装上の欠陥そのもの(境界チェック漏れ等)。発見・悪用の有無に
  関係なくコード上に存在する静的な性質。
- 脆弱性(vulnerability): バグのうち、攻撃者が外部から到達でき、かつ
  セキュリティ上意味のある結果を引き起こせるもの。バグ全部が脆弱性に
  なるわけではない。
- 攻撃(attack): 脆弱性を実際に悪用する行為。狙った入力で欠陥を発火させ、
  狙った結果(コード実行等)を得るプロセス。
- エクスプロイト: その攻撃を実行する具体的なコード/ペイロード。
→ 「バグがある」≠「侵害される」。バグは必要条件でしかなく、攻撃に
  変換できて初めて侵害が成立する。
→ 6-7章の主張の正確な言い直し: nginx/PCRE/zlib/OpenSSLのバグの数は
  通常LinuxとUnikraftで同一(同一ソース)。カナリア/CFI/ASLRは
  バグそのものを消すのではなく「バグを攻撃に変換する」ステップを
  妨害する仕組み。Unikraftではこれが軒並み無効化されているため、
  同じバグが最後まで攻撃として成立しやすく、到達点もring0に直結する。

============================================================
9. 侵害経路はネットワークだけではない
============================================================
- 6-7章の議論は「外部HTTP攻撃者がnginxを乗っ取る」という特定の脅威
  モデルに限定した話であり、一般には侵害経路は複数ある:
  1. サプライチェーン(ビルド時点): Kraftfileが参照するUnikraft
     ライブラリ/nginxソース自体の改ざん。リクエストが1本も届く前に
     成立する。
  2. ホスト側からの直接アクセス: ホストに侵入済みの攻撃者は
     /proc・ptrace、あるいは本プロジェクト自身が使うQEMU monitor
     socket(mon.sock)やgdbstub経由でゲストメモリ/レジスタを直接
     読み書きできる。README「Notes for later phases」でgdbstubを
     `tcp::PORT`(全interface待受)ではなく`tcp:127.0.0.1:<port>`に
     限定した理由はまさにこれ -- HTTPリクエストを介さずゲストの
     全メモリ読み書き権限を握れる経路が実在するため。
  3. ホスト自体が信頼できない場合: ゲスト側のring0/ASLR/カナリアの
     有無は無意味(ホストからは常に全て見え放題)。
- 「外部HTTPのみが攻撃者に見える唯一のインターフェース」という前提
  (今回の脅威モデル)においては、ネットワークが事実上唯一の現実的な
  経路になる。上記1・2は「ビルドパイプラインへのアクセス」「ホストへの
  既存アクセス」という、より強い前提を要する別の攻撃者モデルの話。

============================================================
10. 攻撃対象は「ネットワーク系ライブラリ」に限らない(データフロー)
============================================================
- 判断基準は「ネットワーク系ライブラリかどうか」ではなく「攻撃者が
  指定したデータがそのコードまで(直接・間接問わず)届くかどうか」。
- 実際、6章で挙げたPCRE/zlib/OpenSSL/リゾルバはいずれもネットワーク
  I/Oをするコードではないが、生パケット -> lwip(TCP/IP再構成) ->
  nginx(HTTP解析) -> PCRE(URL正規表現照合) -> zlib(gzip展開) ->
  vfscore(パスでopenat/pread64) -> (TLS有効ならOpenSSLが最初に触る)
  というデータフローに沿って攻撃者データが流れ着くため攻撃対象になる。
- 対象から外れるのは「ネットワーク系でない」コードではなく、
  「攻撃者が中身・タイミング・回数のどれにも一切影響を与えられない
  コード」(起動時一度きりの初期化、書き換え不能な設定読み込み等)のみ。

============================================================
11. 「入口を防ぐ」だけでは大丈夫にならない理由
============================================================
- 公開Webサーバーの目的は「見知らぬ・信頼できないクライアントからの
  リクエストを受け付けて応答すること」そのもの。悪意あるデータか否かは
  ある程度パースしないと判定できないため、入口を完全に塞ぐ=サービスを
  止めるのと同義になり、両立しない。
- ファイアウォール/レートリミット/WAFで一部だけ通しても、通す部分は
  結局nginxやPCRE/zlib/OpenSSLまでデータが届くため攻撃対象は減らせても
  消えない。TLS(OpenSSL)を有効にすると、復号のためにHTTPパーサより
  先に攻撃者データへ触れるコードが増えるケースすらある。
- 現実的な対策は3方向:
  1. 届く範囲(攻撃対象)を減らす: 不要モジュール無効化、パッチ適用。
     ただし未知バグ(0-day)は原理的に潰しきれない。
  2. 届いた後の被害を減らす(多層防御): カナリア/CFI/ASLR。この
     Unikraft構成では軒並み無効化されているのが元々の問題点。
  3. 防ぎきれない前提で、侵害の発生自体を外部から観測する(VMIの
     存在意義、0章に回帰)。

============================================================
12. VMIで観測すべき対象(優先順位)
============================================================
実装コストが低い順:
  1. syscall列/引数の異常検知(新規メカニズム不要): Phase 4で確立
     済みの正常系パターン(accept4->epoll_ctl->recvfrom->openat->
     newfstatat->pread64->writev->close + 定期gettimeofday/
     clock_gettime/epoll_wait)からの逸脱を検知。本来出ないはずの
     execve、webroot外へのopenat、起動後のPROT_EXEC付きmmap等。
     monitor.py/capture.jsonlへの分析レイヤー追加のみで実装可能。
  2. LSTAR/STAR MSR書き換えの監視(既存GDBブレークポイント機構を流用):
     plat/common/include/x86/cpu.h:269-279のwrmsrl命令アドレスに
     ブレークポイントを追加。起動時1回だけがヒットするのが正常系
     -- 起動完了後に再度ヒットすればsyscallハンドラ乗っ取りのほぼ
     確実な証拠。新しいVMIメカニズム(TCG plugin等)を待たずに現行
     GDBスタブ方式のまま追加できる。
  3. 制御フロー/コード整合性監視(EPTベース、次フェーズ待ち):
     ASLR/CFI不在のため、ROP/シェルコード実行は既知の正規コード
     範囲外への命令ポインタ逸脱として外部から検出しやすい(アドレス
     固定だからこそ「正規範囲」を静的に把握できるという逆説的利点)。
     ただしTCG plugin/nested kvmiサンドボックスの技術選定が前提。

============================================================
13. なぜsyscallを観測点として選ぶか
============================================================
- syscallは「意図が外部影響のある行動に変わる」唯一の境界。メモリ内
  だけで完結する処理は、syscallを呼ばない限り外部からは「何も起きて
  いない」のと区別がつかない。攻撃者の最終目的は必ずどこかでsyscall
  という行動に変換される。
- 他の候補との比較:
  - virtio-net MMIO(自然にVM Exitする境界): ネットワーク送受信の
    生バイトしか見えず、ファイル操作/メモリ権限変更/時刻取得等は
    見えない。
  - MSR書き換え監視: 「syscallハンドラ乗っ取り」という単一の特定
    攻撃手法にしか反応しない狭いシグナル。
  - syscallはファイル・ネットワーク・メモリ・時刻・プロセスという
    全リソースカテゴリを1つの統一インターフェースでカバーする唯一
    の観測点。
- Phase 4で「正常系の正解」がsyscall名の列という扱いやすい抽象度で
  既に確立済み -- 異常検知の土台として実用上の利点が大きい。
- これは業界標準の発想と同じ: auditd/seccomp/Falco(eBPF)等の通常
  Linuxの侵入検知も同じ理由でsyscallを標準の観測点にしている。本
  プロジェクトはこれをゲスト内フックではなくVMI(ゲスト外)から行う
  -- 理由は0章の「ゲスト自己申告は侵害後信頼できない」。

============================================================
14. ELFアプリをロードしないUnikernel(nativeモード)のsyscall
============================================================
- 1章のwrmsrl(X86_MSR_LSTAR, _ukplat_syscall)は、app-elfloaderが
  無改造のLinux ELF(nginx)をロードする「バイナリ互換モード」限定の
  仕組み。nginxは実際にx86のsyscall命令を発行するため、Unikraftは
  これをトラップして自前実装に転送する必要がある。
- Unikraft本来のnativeモード(アプリがUnikraft自身のAPI/musl・
  newlib向けlibcに対して直接コンパイルされる)では、open()等の呼び
  出しは実行時トラップではなく**リンク時に解決される普通のC関数
  呼び出し**(例: vfscore_open()を直接呼ぶ)。CPUのsyscall命令は
  一度も発行されず、STAR/LSTAR設定もsyscall.S/_ukplat_syscall/
  ディスパッチテーブルも不要。アプリ+Unikraftライブラリは最初から
  1つの静的リンク済みバイナリで、「syscallで実行主体を切り替える」
  という概念自体が存在しない。
- オーバーヘッドは、Phase 3計測の95-99%増(VM Exit往復コスト)どころ
  か、通常Linuxのカーネル/ユーザ境界トラップのコストすら発生しない
  (単なる関数呼び出しでコンパイラがインライン化しうる)。これが
  Unikernel本来の性能上の売り文句であり、7章で述べた「バイナリ互換
  モードはこの恩恵を放棄している」の具体的な中身。
- VMIへの含意: nativeモードでは"_ukplat_syscallという1点で全syscall
  を横断的に捕捉できる"という前提が崩れる。全リクエストが通る単一の
  ディスパッチ点(chokepoint)が存在しないため、リソース種別ごとに
  個別の関数(vfscore_open、lwipのソケット関数、uktimeのクロック
  関数等)へ個別にブレークポイントを張る必要がある。

============================================================
15. 両モード(バイナリ互換/native)に対応できる観測方法
============================================================
- 結論: トラップ機構(syscall命令/LSTAR)ではなく、その先で実際に
  処理をしている実装関数(uk_syscall_r_*/vfscore/lwipの各関数)自体に
  ブレークポイントを張る。
- 理由: バイナリ互換モードのディスパッチ経路(_ukplat_syscall ->
  uk_syscall6_do_e() -> raxでディスパッチテーブルを引く ->
  uk_syscall_r_<name>()を呼ぶ)も、nativeモード(アプリソースが
  uk_syscall_r_<name>相当を直接呼ぶ)も、**最終的に同じ実装関数を
  同じアドレスで呼んでいる**点は共通。違いは「その関数を誰が/どう
  呼ぶか」(トランポリン経由 vs 直接呼び出し)だけ。観測点を
  「トラップの入口」から「実装関数そのもの」へ1段下げることで
  呼び出し経路の違いを吸収できる。
- 副次的メリット: syscall_table.py(raxからsyscall名への逆引き)が
  不要になる -- ブレークポイントを張ったアドレス自体が関数の識別子
  になるため。
- 未検証のトレードオフ:
  - 観測点が1個(現状)から185個(Phase 2で確認済みの提供syscall数)
    に増える。GDB/QEMU的には複数ブレークポイント自体は問題なく
    扱えるが、管理対象アドレスは増える。
  - インライン化のリスク: nativeモードでコンパイラがuk_syscall_r_*
    呼び出しをインライン展開すると、独立したシンボル/アドレスとして
    残らない可能性がある。ただしバイナリ互換モードのディスパッチ
    テーブルがこれらを関数ポインタとして参照する必要があるため、
    構造的に非インライン・安定アドレスであることが要求されている
    可能性が高い -- 未確認の推測であり、実際のUnikraftのビルド設定
    (__attribute__((noinline))等の有無)を確認して検証すべき点。

============================================================
16. 通常Linuxでも「侵害後はVMIが必要」という論理は成立するか
============================================================
- 成立する。0章の論理(ゲストの自己申告は侵害後信頼できない)は
  Unikraft固有ではなく、一般的な話。実際にDRAKVUF等のVMI型マルウェア
  解析ツールはLinux/Windows VM向けに存在し、カーネルルートキットが
  auditd/Falco(eBPF)/ps/strace等(すべてカーネル自身の機能に依存)を
  偽装・無効化し得ることへの対策として使われている。
- ただし「その状態への到達難易度」がUnikraftとは大きく異なる:
  - 通常Linux: 「アプリ侵害」(例: nginxがwww-data権限で乗っ取られる)
    と「カーネル侵害」(ルートキットが入り、in-guest観測が信頼できなく
    なる)は別の2段階。後者にはユーザ空間RCEに加えて別のカーネル脆弱性
    による特権昇格(ASLR/SMEP/SMAP/カナリア突破)が必要。大多数の侵害は
    1段目止まりで、その間はauditd/Falcoは有効な観測点であり続ける。
  - Unikraft(バイナリ互換モード): ring0固定・カナリア/CFI/ASLRなし
    (6-7章)のため、1段目のRCEがそのまま2段目(カーネル相当のコード
    実行)を意味する。「in-guest観測が信頼できなくなる状態」への到達
    コストが、通常Linuxでは「高度な侵害」だったものが、ここでは
    「最初の1個のバグ」まで下がっている。
→ 結論: VMIの必要性そのものは普遍的(Unikraft固有ではない)が、
  Unikraftではその必要性が発動する閾値が極端に低く、ほぼ常に発動条件
  を満たしてしまう、という言い方が正確。

============================================================
17. 単一アドレス空間で実行されることのメリット(性能面)
============================================================
1章の「CS/SS両方0x08=ring0固定」という性質は、セキュリティ面では
7章の通りデメリット(多層防御の喪失)だが、性能面では明確なメリットに
なる。通常OSが「侵害の被害範囲を抑えるために払っているコスト」を、
境界自体を消すことで丸ごと免除される、という関係:

- 特権遷移(ring3→ring0)のコスト自体が発生しない: 通常Linuxは
  `syscall`命令でCPLが実際に3→0に切り替わり、SMEP/SMAP等のハード
  ウェアチェックが毎回走るが、Unikraftはそもそも切り替えがないので
  このチェック自体が省略される。
- copy_from_user/copy_to_userが不要: 信頼境界がないので、ポインタを
  そのまま渡せばよく、ユーザ/カーネルバッファ間コピーが要らない。
- TLB/ページテーブル切り替えが不要: KPTI(Meltdown対策のKernel Page
  Table Isolation)は「syscallのたびに割高なTLBフラッシュを強制する」
  パッチで、近年のLinuxのsyscallオーバーヘッド増加の主因の一つ。単一
  アドレス空間はこの種の対策自体が構造的に不要(分離すべきページ
  テーブルが最初から存在しない)。
- コンパイラによる境界超えの全体最適化: 14章の通りnativeモードでは
  syscall相当の呼び出しがリンク時に解決される普通の関数呼び出しになり
  インライン化・LTOの対象になる。通常OSは「ユーザ空間の呼び出し」と
  「カーネル内実装」が別最適化単位だが、Unikernelはアプリ+ライブラリ
  全体が1つの静的リンク済みバイナリ。
- プロセス管理機構自体の単純化: マルチプロセス/fork-exec/複数ページ
  テーブル管理が不要なため、メモリフットプリントが小さく起動が速い
  (Unikernelの「秒未満起動」の技術的根拠)。

============================================================
18. Unikernelのセキュリティ上の利点(攻撃対象=TCB削減)
============================================================
7章で区別した(1)テナント分離(2)同一アプリへの多層防御のうち、
Unikernelが正当に享受できるのは(1)を捨てることで得られる
「攻撃対象(TCB)自体の削減」である。具体的には:

- 不要なカーネルサブシステムが物理的に存在しない: 汎用ドライバスタック、
  名前空間/cgroup(コンテナ脱獄CVEの温床)、マルチユーザ権限モデル、
  動的モジュールロード機構(ルートキットの主要侵入経路)。
- コード量削減による絶対バグ数の減少(8章のバグ/脆弱性の区別): 提供
  syscallは185個のみ(README Phase 2)、フルLinuxカーネルの数百万行に
  対し実装コードが遥かに少ない。
- 他プロセス/他テナントがいない=水平展開の余地がない: 1インスタンス
  1アプリなので、乗っ取った後に狙う「隣人」が存在しない。
- 静的・不変イメージ: 明示的にリンクしない限り/bin/sh等の汎用バイナリ
  が存在せず、living-off-the-land的なpost-exploitationの道具がない。

**留保(7章の結論の再確認)**: これらはすべて「カーネル側」の削減で
あり、本検証対象(app-elfloaderのバイナリ互換モードで無改造nginx+
PCRE+zlib+OpenSSLを実行)は**アプリ側の攻撃対象を一切削減していない**。
Unikernel本来の強み(TCB削減)をカーネル側だけ部分的に享受しつつ、
弱み(多層防御の喪失、6-7章)は全面的に負っている非対称な位置づけ。

============================================================
19. _ukplat_syscall の詳細実装 (plat/common/x86/syscall.S:43-336)
============================================================
6段階に分かれる:

1. 前処理・スタック切替(43-77行目): cli → swapgs(GSをUnikraftの
   struct lcpuへ) → アプリのrspをr11に退避 → 補助スタック(auxsp)へ
   切替(アプリのスタックを壊さないため)。
2. トラップフレーム構築(79-213行目): swapgsで戻した後、eflags/cs/
   rcx(戻り先rip)/orig_rax/rdi/rsi/rdx/rcx/rax/r8-r15/rbx/rbpを補助
   スタックへ手動push。CPUがハードウェアでやる特権遷移時のレジスタ
   退避を、特権遷移がないUnikraftでソフトウェア的に再現している。
3. 拡張コンテキスト保存(214-253行目): sti(フレームが安全に組めたので
   割込み再許可) → ukarch_ectx_sanitize/store(FPU/SSE/AVX状態) →
   ukarch_sysctx_store。
4. Cハンドラ呼び出し(254-264行目): movq %rsp,%rdi; call
   ukplat_syscall_handler -- ここが実ディスパッチの入口。
5. 復帰処理(266-321行目): cli → ectx/sysctx復元 → 2で積んだレジスタを
   逆順にpop(rax等はハンドラの戻り値で書き換わっている) → 元のアプリ
   スタックポインタへ復帰。
6. 呼び出し元への復帰(324-334行目): sti; jmp *%rcx。sysret命令では
   ない(コード内コメントがHermiTux論文を明記): sysretはCPLを0→3に
   戻す命令だが、Unikraftは特権レベルを変えていない(CS/SS常に0x08)
   ため、sysretを使うと逆に不要な特権遷移が発生してしまう。よって
   普通の関数リターンと同じ「戻りアドレスへの単純jmp」で済ませる。

結論: _ukplat_syscallは「CPUがハードウェアで自動的にやるはずの特権
遷移・レジスタ退避を、特権遷移が存在しないUnikraftの世界でソフト
ウェア的に手作業で再現しているトランポリン」。実処理は一切行わず、
レジスタをトラップフレーム形式に整えてukplat_syscall_handlerに渡し、
戻り値を元のレジスタ位置に戻して呼び出し元へjmpするだけ。

============================================================
20. ukplat_syscall_handler の詳細実装
    (lib/syscall_shim/uk_syscall_binary.c:68-117)
============================================================
_ukplat_syscallが組み立てたstruct uk_syscall_ctxを受け取り、実処理
本体を呼ぶ前後の処理を行うCレベルのディスパッチャ。5段階:

1. システムレジスタをUnikraft用に切替(90-91行目): アセンブリ側は
   execenvを退避しただけで、アクティブなシステムレジスタはまだアプリ
   のもの。ここで初めてUnikraft自身のsysctxをukarch_sysctx_load()。
2. TLS切替(93-98行目、CONFIG_LIBSYSCALL_SHIM_HANDLER_ULTLS時): アプリ
   のTLSポインタからUnikraft自身のTLSポインタへ。
3. entryフック実行(100-104行目): uk_syscall_entertab_run()。
   CONFIG_LIBSYSCALL_SHIM_DEBUG_HANDLER有効時はbinary_syscall_debug_
   handler(120-141行目)がここでsyscall名・引数をデバッグ出力。
4. 実ディスパッチ(106行目): execenv->regs.__syscall_rret0 =
   uk_syscall6_do_e(execenv); -- 「どのsyscallか」の判定自体はここに
   委譲。
5. exitフック実行(108-112行目): uk_syscall_exittab_run()。
   CONFIG_LIBSYSCALL_SHIM_STRACE有効時はbinary_syscall_strace
   (144-180行目)がここでstrace形式のログを出力
   (Phase 4のground truthはまさにこの出力)。

備考: entertab/exittabフック機構は、GDBブレークポイントより低
オーバーヘッドな新しい観測点の第3の選択肢になり得る(15章のトラップ
入口 vs 実装関数そのもの、という二択に対する別解)。

============================================================
21. syscall実行の全体フロー (gettimeofdayを具体例に、コード引用付き)
============================================================
0. 起動時1回のみ: wrmsrl(STAR, CS/SS=0x08x2); wrmsrl(LSTAR,
   _ukplat_syscall);  (cpu.h:269-279)
1. nginx: libcのgettimeofday(&tv,NULL)がrax=96,rdi=&tv,rsi=NULLを
   セットしsyscall命令実行。
2. CPUハードウェア(Unikraftのコード外): rcxに戻り先RIP、r11にRFLAGS
   を自動退避。RIP=LSTAR、CS/SS=STARの0x08(特権遷移なし)。
3. _ukplat_syscall(19章参照)がトラップフレーム構築、
   call ukplat_syscall_handler。
4. ukplat_syscall_handler(20章参照)がsysctx/TLS切替、entryフック、
   uk_syscall6_do_e(execenv)呼び出し。
5. uk_syscall6_do_e: uk_syscall6_do.awkがprovided_syscalls.inから
   ビルド時に自動生成したswitch文
   (.unikraft/build/libsyscall_shim/uk_syscall6_do.c:2027-2040、実物):
     case SYS_gettimeofday:
       ret = uk_syscall_do_gettimeofday(execenv->regs.__syscall_rarg0,
                                         execenv->regs.__syscall_rarg1);
6. uk_syscall_do_gettimeofday(UK_SYSCALL_R_DEFINEマクロ経由)→
   lib/posix-time/time.c:158-162のuk_syscall_r_gettimeofday→
   uk_sys_gettimeofday(146-156行目): ukplat_wall_clock()でTSCを直読み
   するだけ。ここで初めて「本当の処理」が実行される(3章の「大半の
   syscallはVM Exitを起こさない」の具体例そのもの)。
7. 戻り値(0)がuk_syscall6_do_eのret→ukplat_syscall_handler内で
   execenv->regs.__syscall_rret0(トラップフレームのraxスロット)へ
   書き戻り(uk_syscall_binary.c:106)。
8. _ukplat_syscallに戻り、レジスタ復元(raxに戻り値0)、元のアプリ
   スタックポインタ復元、jmp *%rcxでnginxのsyscall命令の次へ復帰。

============================================================

============================================================
23. ホスト側実行の具体例: virtio-netのkickが唯一のVM Exit契機
============================================================
accept4/recvfrom等の送受信系syscallを追うと、最終的に
drivers/virtio/pci/virtio_pci.cのvirtio-netドライバに到達する。
ゲストが新しいディスクリプタをvirtqueueに積んだ後、ホストに気づかせる
「kick」の実装:

    // virtio_pci.c:115-123
    static int vpci_legacy_notify(struct virtio_dev *vdev, __u16 queue_id)
    {
        struct virtio_pci_dev *vpdev = to_virtiopcidev(vdev);
        virtio_cwrite16((void *)(unsigned long) vpdev->pci_base_addr,
                        VIRTIO_PCI_QUEUE_NOTIFY, queue_id);
        return 0;
    }

virtio_cwrite16 → virtio_cwrite_bytes (virtio_config.h:181-205) →
ioreg_write16()、これはx86の`out`命令(PIOアクセス)。PIO命令はx86
仮想化の設計上、常にVM Exitとしてトラップされる(VMXのI/O exiting)。
gettimeofdayのTSC読み取りやopenatの構造体操作のような普通の命令列は
KVMが一切関知しないのに対し、この`out`命令だけがCPUを強制的に
VMXルートモード(ホスト側)へ遷移させ、QEMUのvirtio-netエミュレーション
コードを起動する。受信(RX)方向はこの逆で、ホストが実NIC/tapから
受信したパケットをvirtqueueに書き込み、ゲストへ仮想割り込みを注入する
(syscall実行タイミングとは非同期)。

    gettimeofday, openat 等:  ゲスト内で完結 → VM Exit 一切なし
    accept4, recvfrom 等:     lwIPバッファ操作等はゲスト内
                              → 最後にvpci_legacy_notify() の out命令
                              → ここだけがVM Exit

============================================================
24. 「ゲスト側/ホスト側」は物理的に別のCPU・メモリという意味ではない
============================================================
重要な誤解しやすい点: ゲストとホストは物理的に同じCPUコア・同じ
物理RAMを使っている。KVM(TCGエミュレーションではなくハードウェア
仮想化支援)を使っている以上、ゲスト命令はCPUが直接ネイティブ速度で
実行している。「ゲスト側/ホスト側」という区別は物理資源の違いではなく
同じCPUコアが取りうる2つの動作モードの違いを指す:

- VMX root モード: ホスト(Linuxカーネル本体、KVMモジュール、QEMU
  プロセス)が動くモード。
- VMX non-root モード: ゲスト(Unikraft nginx)が動くモード。

これまで議論してきたring0/ring3(1章)は、どちらもnon-rootモードの
「内側」の話であり、root/non-rootの区別はさらにその外側にある別軸。

メモリも同様: ゲストが見る「物理アドレス」(Guest Physical Address)
はEPT(Extended Page Tables)という追加の変換層を経由して、QEMU
プロセスが確保した本物のホスト物理メモリ(Host Physical Address)に
マッピングされている。ゲストのRAMは本当に存在する物理メモリの一部で、
ただ0番地から始まる連続領域に見えるようEPTが変換しているだけ。

「ホストから見えない」の実体: QEMUのvCPUスレッドはKVM_RUN ioctlを
呼んだ状態でブロックしている。CPUがnon-rootモードで実行している間、
ホスト側ソフトウェア(QEMU/Linuxカーネル)はそのスレッドが眠っている
ため本当に何もしていない。VM Exit(root モードへの遷移)が起きる条件は
事前定義されたトリガーのみ: PIO/MMIOアクセス(23章)、EPT違反、特定
命令のインターセプト設定(CPUID/RDMSR/WRMSR等)、外部割込み・例外、
ソフトウェアブレークポイント(int3、VMIツールが使う手段)。syscall命令
や通常のメモリアクセスはこれらのどれにも該当しないため、CPUはnon-root
モードに留まり続け、ホストは本当に何も観測できない。

    | 物理資源                       | 動作モード
    ゲスト実行 | ホストと同じCPUコア・同じ物理RAM(EPT経由) | VMX non-root
    ホスト(QEMU/KVM) | 同上                                    | VMX root

「ゲスト側で完結する」「ホストから見えない」は「別マシンで動いている」
ではなく「同じCPUがnon-rootモードに留まり続け、root モードへの強制
遷移(VM Exit)が起きない」という意味。VMIがint3で人工的なトラップを
仕掛けるのは、まさにこの「non-root→root遷移」を意図的に発生させる
ための手段。

25. uk_syscall6_do_e / uk_syscall_do_<name> / uk_syscall_r_<name> の違い
    (lib/syscall_shim/include/uk/syscall.h)
============================================================
- uk_syscall6_do_e (uk_syscall6_do.c、awk自動生成、全syscall共通で1個):
  raxを見てswitch分岐し、該当する uk_syscall_do_<name>()(またはexecenv
  版 uk_syscall_do_e_<name>())を呼ぶだけの「ルーター」。
- UK_SYSCALL_R_DEFINE/UK_LLSYSCALL_R_DEFINEマクロ(syscall.h:379-547)は
  1回の呼び出しで3つの関数を同時生成する:
    - uk_syscall_r_<name>()  : entertab/exittabフックを自前で発火して
      から実装本体 __uk_syscall_r_<name>() を呼ぶ。native/直接呼び出し
      向け。
    - uk_syscall_do_<name>() : フックなしで実装本体を直接呼ぶ。
      uk_syscall6_do_eからのみ呼ばれる。
    - uk_syscall_e_<name>()  : rname()を呼び、戻り値が負のエラーエンコ
      ード値ならerrno設定+-1に変換するlibcスタイルの外側ラッパー。
- なぜ2系統(do/r)に分かれているか: ukplat_syscall_handler(20章)は
  uk_syscall6_do_e()全体を uk_syscall_entertab_run()/exittab_run() で
  外側から囲んでおり(uk_syscall_binary.c:104,111)、フックは既にそこで
  1回発火済み。もしuk_syscall6_do_eが"_do_"ではなく"_r_"を呼んでいたら、
  "_r_"内部の_uk_syscall_wrapper_do_entertab(NULL)呼び出しと合わせて
  フックが二重発火し、strace出力が1syscallにつき2行(しかも片方は
  execenv付きの正確なログ、もう片方はNULL渡しで引数情報欠落)という
  不整合を起こす。"_do_"はこの二重発火を避けるための、外側に既に
  フックがある経路専用の薄いラッパー。
- 実装本体(__uk_syscall_r_<name>、マクロ末尾の{ ... }ブロックがこの
  関数の中身になる)はdo/r両方から共有される唯一のロジック。例:
  time.c:158-162のgettimeofdayは uk_sys_gettimeofday() へさらに1段
  delegateするが、vfscore/main.c:114-136のopenatのように実装が直接
  ブロック内に書かれているケースもある。

26. 全185syscall共通の実行フロー(chokepointの正体)
============================================================
binary互換モードの全syscallは以下の前半を完全に同一のアドレス・経路
で通過し(chokepoint)、⑤で初めてsyscall番号ごとに分岐する:

  ①nginx: rax=番号,引数をセットしsyscall命令発行
  ②[CPU] RIP←LSTAR、CS/SS←STAR(0x08固定、特権遷移なし)
  ③_ukplat_syscall(syscall.S) ※唯一のchokepoint、全syscall共通アドレス
  ④ukplat_syscall_handler: entertab_run→uk_syscall6_do_e→exittab_run
  ⑤uk_syscall6_do_e: raxでswitch分岐 → 185通りのuk_syscall_do_<name>
  ⑥uk_syscall_do_<name>(フックなし薄いラッパー)
  ⑦__uk_syscall_r_<name>(実装本体。担当ライブラリはリソース種別で
    異なる: posix-time/vfscore/lwip+posix-socket/ukvmem等)
  ⑧-A 大半のsyscall: ゲスト内で完結、VM Exitなし
  ⑧-B accept4/recvfrom等ネットワーク系のみ: 最後にvirtio-netのout命令
    (PIOアクセス)でVM Exit(23章)
  ⑨⑩ 戻り値巻き戻り→_ukplat_syscallでレジスタ復元→jmp *%rcxで復帰

12・15章の「chokepoint」とは③のことで、ここに1個ブレークポイントを
置くだけで全185syscallを横断的に捕捉できる(ただしbinary互換モード
限定、14章参照)。

============================================================
27. 復帰処理(⑨⑩)の補足: 「復元」と「上書き」の違い
============================================================
syscall.S:266-334の復帰処理は、行き(トラップフレーム構築)で退避した
値を全て逆順に読み戻すだけの作業。ただし rax だけは例外で、行きは
syscall番号だったのが、ukplat_syscall_handlerが同じトラップフレーム
のraxスロットに戻り値を上書きしているため、popされる時には戻り値に
変わっている。他の汎用レジスタ・FPU/SSE状態・システムコンテキストは
全て文字通りnginxが割り込まれる直前の値に「復元」される。
最後にsysretではなくjmp *%rcxで戻るのは、Unikraftがそもそも特権
レベルを変えていない(19章⑥)ため。

============================================================
28. VM Exitに依存しないVMI手法の類型
============================================================
4章で述べたTCG plugin以外にも、VM Exitに依存しない観測手法は存在する:
  - TCGプラグイン(エミュレーション内フック): 唯一の「確実に捕捉でき、
    かつトラップ不要」な手法(4章の結論通り)。
  - 物理メモリの受動的ポーリング: LibVMIのpmemaccess系。イベントでは
    なく定期サンプリングなので、短命なsyscallイベントの見逃しが原理的
    な弱点。
  - Intel PT(Processor Trace): 制御フローをハードウェアが常時記録、
    バッファドレイン時のみVM Exit。命令アドレスの流れは追えるが
    syscallの引数(レジスタ値)は別途読む必要がある。
  - 帯域外DMAベースの物理メモリアクセス: ハイパーバイザ非信頼モデル
    向けの特殊な手法。
  - Record & Replay(PANDA等): 事後解析専用、リアルタイム検知には
    不向き。
この案件の「syscallイベントを確実に捕捉する」という要件では、TCG
pluginが引き続き唯一の実用的な非VM-Exit手法。

============================================================
29. nativeモードはこのプロジェクトでは未構築(Kraftfileで確認済み)
============================================================
14章で議論した「nativeモード」はUnikraft一般の話であり、本プロジェクト
のKraftfile(source: unikraft/app-elfloader.git)を確認したところ、
実際にビルドされているのはapp-elfloader(バイナリ互換モード)のみ。
つまり14〜15章の議論は理論的な比較・将来の一般化のためのものであり、
本プロジェクトで実際にnativeモードの構成を検証したわけではない。
「nativeモードでは監視の"手段"(トラップ)は無意味になるが"必要性"は
消えない」という結論(15章)自体は論理的に妥当だが、実際にmuslポート
がuk_syscall_r_<name>を直接呼ぶのか、それとも別の低レイヤー関数を
呼ぶのかは未検証(15章の「未検証のトレードオフ」参照)。

============================================================
30. syscallという観測対象の限界: ABI依存性とより頑丈な代替
============================================================
syscallは「Linuxバイナリ互換ABI」という人為的な取り決めであり、CPU/
ハードウェアが本質的に持つ概念ではない。nativeモードではこの単位自体
が存在しない(14章)ことがその証拠。より「ハードウェアの事実」に近い
代替候補:
  - 制御フロー/コード整合性監視(EIPが既知の正規コード範囲外に逸脱):
    命令ポインタという純粋なハードウェアの事実に基づき、ABI非依存・
    両モード共通。ASLR/CFI無し(6-7章)というこの構成の核心的弱点を
    逆手に取り、正規範囲を静的に把握できる。ただしdata-only攻撃
    (既存の正規コードだけを使い、データ構造だけ書き換える攻撃)には
    無力。
  - データフロー/taint追跡: 最も厳密だが実装コスト大(TCG必須)。
syscall監視は「Phase 4のground truthがある」「industry標準」という
実利はあるが、ABIレベルの抽象化に依存している点で、制御フロー監視
より根本性で劣る。

============================================================
31. 攻撃者によるブレークポイント回避(関数を呼ばず直接メモリ操作)
============================================================
6章の通りring0を得た攻撃者は任意の物理メモリ/ページテーブルの読み書き
が可能。これは「関数呼び出しという規約に従う理由がない」ことを意味し、
syscall監視・実装関数レベルのブレークポイント(15章)の両方が同じ弱点
を持つ:
  - vfscore_write()等の正規関数を経由せず、ファイル内容の物理メモリを
    直接書き換えられる。
  - virtio-blkへの永続化も、正規のvfscore内部処理を経由せず、リクエスト
    構造体を直接手で組み立ててキューに積むことができる。
  - 制御フロー監視でさえ、data-only攻撃(命令ポインタが正規範囲を一度
    も出ない)には無力。
「関数が呼ばれたか」という前提はソフトウェアの約束事に過ぎず、ring0
権限を持つ攻撃者にとっては単なる選択肢の1つでしかない。

============================================================
32. 32節への対抗策: VMX root/non-root境界に根ざした監視
============================================================
24章のroot/non-root区別は、ring0/ring3と異なりゲストが絶対に越えられ
ない境界。これに基づく監視は「関数が呼ばれたか」ではなく「物理的に何が
変化したか」を見るため、31章の回避策が効かない:
  - EPTベースの物理メモリ書き込み監視: 保護対象ページ(例: webrootの
    ファイル内容)をEPT経由で書き込み禁止にしておけば、攻撃者がどんな
    経路(正規関数/直接メモリ操作)を辿ろうと、実際にそのページへ書いた
    瞬間にEPT violationで捕捉される。EPT設定自体はホスト管理下にあり、
    ゲストのring0権限からも触れない。
  - virtio-netのkick(23章)も同様に、ホストへの通知という仮想ハード
    ウェアプロトコル上必須の動作であり、関数呼び出しを介さず直接キュー
    を操作しても回避できない。
  - 実装手段の現実的な評価(本プロジェクトのインフラを前提):
    - ハードウェアウォッチポイント(GDBのwatch、DR0-3レジスタ)は
      phase1_manual_test.gdbのコメントで既に「KVM_SET_GUEST_DEBUG
      経由のハードウェアブレークポイントには既知の信頼性バグがある」
      と判明しており不採用。
    - KVMのdirty-page tracking(KVM_MEM_LOG_DIRTY_PAGES+
      KVM_GET_DIRTY_LOG、内部実装はEPT書き込み保護+violationで
      ライブマイグレーション用に元々存在)は有望だが、現状の
      mon.sock(素のHMPテキスト、README.md:181-182)には該当コマンド
      がなく、QEMU側への独自コマンド追加(パッチ)か、ゲストRAMの
      バッキングファイルへのmprotect+SIGSEGVによる代替が必要。
    - 保護対象ページの特定は、ASLR無し・静的リンク(17-18章)という
      この構成の性質により、起動後1回GDBでアドレスを特定すれば
      再起動までアドレスが変わらないという利点がある。

33. 攻撃者に何をされたら実害があるか(優先順位)
============================================================
1. コンテンツ改ざん(整合性侵害、最重要): webroot/レスポンス内容を
   書き換えられ、本物の訪問者にマルウェア混入コンテンツ等が配信される。
   被害はサーバー1台から不特定多数の訪問者に拡散する。EPT書き込み
   監視(32章)の直接の防御対象。
2. 秘密情報漏洩(機密性侵害): TLS秘密鍵、バックエンド認証情報等。
   単一テナント(18章)なので「他ユーザーのデータ漏洩」という水平展開
   被害は無く、漏れて困るのはサーバー自身の秘密に限定される。
3. 踏み台化: VMを使って他システムを攻撃(スキャン/スパム/DDoS参加)。
   ネットワーク到達性次第で深刻度が変わる。virtio-net kick監視(23章)
   で検知しうる。
4. (メタレベル)観測手段の無力化: ゲスト内strace等の自己申告機構が
   攻撃者に無効化・偽装される(6章)。実害というより1-3を検知・対応
   する能力そのものの喪失。0章のVMI必要性の直接の理由。
5. 持続的な足場の確立: 静的・不変イメージ(18章)のため再起動で
   リセットされ、この構成では相対的に軽微。ただしサプライチェーン
   経路(9章①、ビルドパイプライン汚染)ならこの限りではない。

これまで議論してきたsyscall監視/関数ブレークポイント/EPT書き込み監視
は、突き詰めると1番(コンテンツ改ざん)を防ぐための手段として位置づけ
るのが最も筋が通る。

============================================================
34. syscall監視の有効性の再評価: 汎用攻撃者 vs 標的型攻撃者
============================================================
31章の「関数を呼ばず直接メモリ操作すれば監視を回避できる」という懸念
は理論的には正しいが、実行に移すハードルを考慮すると評価が変わる:
  - 一般的な攻撃者(自動スキャンボット、既製exploitキット、汎用
    shellcode)のペイロードは、そもそも「OSのサービスを使うこと」
    (シェル起動=execve、ファイル窃取=open/read、外部送信=socket/
    connect)が目的であり、標準のLinux syscall ABIを直接叩く前提で
    書かれている。app-elfloaderのバイナリ互換モードはこれを透過的に
    動かすことが設計目的そのものなので、既製shellcodeは
    「ここがUnikraftである」と気づく必要がなく、わざわざvfscore内部
    構造を解析して直接メモリを書き換える手間をかけない。
  - Phase 4のground truthパターンからの逸脱検知(12章①)は、この
    「一般的な攻撃者」層に対して極めて有効。
  - 31-32章の回避策が現実的な脅威になるのは、「ここがUnikraftだと
    事前調査で把握し、vfscore/virtio内部レイアウトを解析してカスタム
    ペイロードを書く」標的型攻撃者に限られ、これは外部HTTP攻撃者と
    いう脅威モデルの中でも相当レアなケース。
→ 結論: syscall監視は「防ぎきれない完璧な対策」ではなく「コストが
  低く、現実の攻撃トラフィックの大部分(汎用攻撃者層)に効く実用的な
  一次防御」。EPTベースのメモリ整合性監視(32章)は、これをすり抜ける
  少数の標的型攻撃者に対する二次防御として位置づけるのが正確(11章の
  「防ぎきれない前提での外部観測」の具体化)。

============================================================
35. ELF型Unikernel特有の攻撃パターン(外部HTTP攻撃以外)
============================================================
9章で挙げた3経路(サプライチェーン/ホスト直接アクセス/ホスト非信頼)
に加え、「ELFローダーでバイナリをロードする」という構成固有の切り口:
  1. ELFローダー(app-elfloader)自体への攻撃: ロードされるELFファイル
     自体を細工できる立場(デプロイパイプライン汚染)からは、nginxの
     HTTPパーサではなく、Unikraft自身が新規実装したELFパーサ(プログラム
     ヘッダ/セクションヘッダ解析)のバグを直接狙える。サプライチェーン
     攻撃(9章①)の一種だが、狙う対象がnginxではなくUnikraft自身の
     コードである点が異なる。
  2. ネットワークスタック下位層への攻撃: 10章のデータフロー
     (生パケット→lwip→nginx)のうち、lwip(TCP/IP再構成)やvirtio-net
     ドライバのディスクリプタ処理自体のバグを、nginxのHTTPパーサに
     到達する前に突く攻撃。狙うコードがnginx/PCRE/OpenSSLではなく
     Unikraft自身が実装した部分である点が10章の議論の裏返しになる。
  3. 同居する他VMからのサイドチャネル攻撃: Spectre/Meltdown系。
     nginx/lwipのコードを一切攻撃せず、ASLR無し・アドレス固定
     (17-18章)という性質がキャッシュタイミング攻撃の標的アドレス
     特定を容易にする可能性がある。9章③の「ホスト非信頼」の一種だが、
     「同居する別テナントが信頼できない場合」という中間的なケース。
  4. 管理・オーケストレーション面への攻撃: kraft CLI、mon.sock/
     gdbstub等の管理系エンドポイントが誤って外部公開されている場合。
     9章②の一種だが、「攻撃者がホストに侵入済み」ではなく「設定ミス
     による誤公開」という別の前提。README側でgdbstubを127.0.0.1限定
     にしている理由(9章②既出)はまさにこの経路対策。
